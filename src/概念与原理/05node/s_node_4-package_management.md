# npm、Yarn、pnpm 与依赖管理

> 包管理器的目标不只是“把包下载下来”，还包括解析版本、组织依赖关系，以及让团队和构建环境尽可能复现同一套依赖。

## 一、先区分几个概念

- **npm registry**：包的分发服务，npm、Yarn、pnpm 都可以访问兼容的 registry。
- **npm CLI**：一个包管理工具，不等于 registry 本身。
- **package.json**：声明包的元信息、脚本与依赖约束。
- **锁文件**：记录解析出的依赖图、具体版本及完整性等信息，具体字段依工具与格式而异。
- **node_modules / PnP**：依赖在本地如何布局和被解析，不等于“下载源”。

## 二、package.json 中最重要的字段

| 字段 | 用途 | 注意点 |
| --- | --- | --- |
| `scripts` | 定义开发、检查与构建等命令 | `build` 做什么取决于脚本，不是 Node.js 自动赋予的能力 |
| `dependencies` | 通常用于运行或交付所需依赖 | 前端打包项目与服务端部署项目的需求不完全相同 |
| `devDependencies` | 开发、检查、构建等工具 | 构建阶段仍需这些依赖，不能过早只安装生产依赖 |
| `peerDependencies` | 声明期望由使用方提供的兼容依赖 | 常见于插件、组件库；实际安装策略因工具版本而异 |
| `engines` | 声明支持的 Node / 包管理器范围 | 是否严格阻止不兼容安装，取决于工具设置 |
| `packageManager` | 声明项目约定的工具与版本 | 需要开发环境和自动化真正使用该版本 |
| `type` | 确定包中 `.js` 的模块格式 | 不控制 `.mjs` / `.cjs` 的显式格式 |
| `exports` | 定义包对外的入口与子路径 | 有助于限制内部实现被随意导入，也影响 ESM/CJS 入口 |
| `private` | 防止意外发布包 | 不等于把源代码变成保密内容 |

包的类型由使用目的决定，不能认为 `devDependencies` 中的代码永远不会出现在最终前端产物；只要被构建链引入，仍可能进入输出。

## 三、版本范围与锁文件

以稳定主版本 `1.2.3` 为例：

| 写法 | 常见含义 |
| --- | --- |
| `1.2.3` | 精确版本 |
| `~1.2.3` | 通常允许补丁更新，即 `>=1.2.3 <1.3.0` |
| `^1.2.3` | 通常允许向后兼容的次版本和补丁更新，即 `>=1.2.3 <2.0.0` |
| `workspace:*` | 以支持该协议的工具解析本工作区包 |

`0.x` 版本的 caret 范围更收敛，例如 `^0.2.3` 通常不跨到 `0.3.0`；预发布版本也有额外规则。即便版本遵循 SemVer，升级后仍要验证，不应只凭版本号认定完全兼容。

锁文件固定的是解析结果，`package.json` 说明可接受范围，二者需要一起维护。手改约束后不更新锁文件，冻结安装通常会拒绝继续。

**可重复安装仍有环境边界**：Node 版本、包管理器版本、操作系统、CPU 架构、原生模块、可选依赖以及安装脚本，都可能影响结果。锁文件是基础，不是跨所有环境完全相同的保证。

## 四、三种工具的依赖布局

| 工具 / 模式 | 常见特征 | 需要注意 |
| --- | --- | --- |
| npm | 常见使用 `node_modules` 和提升去重 | 某些间接依赖可能恰好可访问，不应依赖这种布局偶然性 |
| Yarn | 不同代际差异较大；现代 Yarn 可选择 PnP 或 node_modules linker | 不能把所有 Yarn 都描述为同一种扁平目录 |
| pnpm | 常见使用内容寻址存储、虚拟存储及链接组织依赖图 | 对直接依赖边界通常更严格，仍受 hoist/linker 等设置影响 |

### pnpm 为什么能节省磁盘？

常见安装模式下，pnpm 把包文件放入可复用的内容寻址存储，通过硬链接或写时复制等方式复用文件（受文件系统与配置影响），在项目的虚拟存储中组织包，再使用符号链接表达依赖关系。

因此不能简单记成“所有文件都是软链接”，也不能认为它只解决下载速度；依赖关系的隔离与共享存储同样重要。

### 什么是幽灵依赖？

某个包没有在当前包中声明，却因为其他依赖被提升等原因恰好能够导入，称为幽灵依赖或未声明依赖。换工具、升级或改变工作区布局后可能失效。

正确做法是：**在哪个包中直接使用，就在那个包中显式声明。** 不要通过盲目开启全面提升来掩盖依赖声明问题。

## 五、本项目如何使用？

本项目当前约定 Node.js 24.x、pnpm 12.14.0，具体以 `.nvmrc`、`package.json` 和锁文件为准。下面仅说明现有流程，不修改工具或发布配置。

```bash
# 按现有锁文件安装；不擅自更新解析结果
pnpm install --frozen-lockfile

# 开发、校验、构建
pnpm dev
pnpm check
pnpm build

# 查看某个依赖为何被引入
pnpm why vue
```

新增依赖前先判断是不是 Node.js 内置能力、已有依赖是否足够。确需添加时，在正确的包中声明，提交 `package.json` 与 `pnpm-lock.yaml`，并验证兼容性。

**不要在同一项目中混用 npm、Yarn 和 pnpm 生成多份相互竞争的锁文件。** 更换工具属于一次有验证要求的迁移，不是换一条安装命令。

## 六、开发、构建与运行是不同阶段

```text
开发：源码 + 类型检查 / lint / 本地服务
    ↓
构建：安装构建所需依赖，转换或打包源码
    ↓
交付：发布实际产物，以及运行所需的文件与依赖
```

前端静态站点构建后可以只部署静态文件；Node.js 服务通常仍需要 Node 运行时，是否需要运行时依赖取决于构建产物是否外部化依赖等策略。不能因为项目都用 pnpm，就把交付方式混为一谈。

Monorepo 可以统一管理多个应用与共享包，但不是把所有依赖都堆进根目录。每个包要声明自己的依赖，构建顺序、包边界与发布策略也要明确。

## 七、依赖安全与维护

- 安装脚本可以执行代码，新增依赖前要评估来源、维护情况和脚本行为；不随意放开所有脚本权限。
- 完整性校验能帮助验证下载内容是否符合锁定结果，但不证明包本身没有恶意逻辑。
- 安全审计是发现已知风险的线索，仍需判断实际使用路径、影响版本和修复兼容性。
- 升级最好分批进行，先读变更说明，再运行类型检查、测试和构建；不要为追逐“最新”而绕过框架的兼容依赖组合。

## 八、学习回顾

> npm、Yarn、pnpm 都能管理依赖，但本地布局和解析策略不同。package.json 描述依赖范围，锁文件记录具体解析结果；要让团队安装可重复，还得统一 Node 和包管理器版本。pnpm 常通过共享内容存储和链接组织依赖，节约磁盘，并减少未声明依赖被偶然访问的问题。项目中我会坚持一种工具、一份对应锁文件，升级后验证真实构建和运行。

**自测：** 为什么提交了锁文件还要统一 Node 版本？`pnpm why` 能解释什么？构建前只安装生产依赖为什么可能失败？Monorepo 子包为什么仍要声明自己的依赖？
